# 人员管理

平台管理统一为「人员管理」和「角色与权限」。人员列表管理档案、任职、工作资格及个人角色；激活与账号保留账号列表、激活审核及加入资格。单人新增与 CSV 导入共用校验、差异计算及事务写入。普通人员档案可以不关联登录账号。

## 导入

普通模板为 `studentId,name,college`，在界面选择实际部门、人员类型、所属校区、任职类型及生效日期。也支持原有高级列覆盖默认值。空白学院、专业、工作资格、角色及授权校区保留已有信息。已有人员状态保持不变。

导入只补充任职、资格和角色。相同部门、类型、授权范围及覆盖生效日期的长期有效记录跳过；主部门任职重叠、资格有效期重叠或角色范围不一致显示冲突，需要在详情中明确结束或调整。存在冲突时整批不写入。

默认保留已有登录授权。管理员单独选择「按非空授权校区列替换」才会修改已有账号校区；空白授权列始终保留。高级 `accountRole` 只配置尚未激活人员的邀请类型，不修改已有账号。

`POST /api/members/import` 首次返回 `previewToken`、逐人 `changes`、`conflicts` 及 `summary`（`created/updated/skipped/conflict`）。确认时提交同一 CSV、默认设置、账号校区更新方式和 `previewToken`，并设置 `confirm: true`。名单、任职、角色、邀请、部门或权限发生变化后需要重新预览。`count` 表示实际新增或更新的人数，不含跳过项。

无变化导入不写审计，不增加成员、邀请或账号版本。资料变化不撤销登录；任职、工作资格、角色及登录校区变化才会更新认证版本。所有写入与逐人审计在同一事务中提交。

## 权限与部门

合并入口保持 `members.manage`、`roles.manage`、`accounts.manage` 隔离。人员详情中的密码及账号授权操作仍由账号接口独立校验；仅有账号管理权限的管理员从统一入口进入激活与账号。

部门是跨校区共用的字典，新增、改名及启停要求**全局 `settings.manage`**。系统设置管理员可直接进入部门维护；仅有设置权限时不会读取人员或账号列表。校区或部门范围的设置权限不能修改全局字典。部门停用不删除任职或历史记录，并从新增任职选项中移除。更新使用 `revision` 防止并发覆盖；无需数据库迁移。

## 性能与验证

导入使用一次 SQL 查询加载整批成员、账号、任职、资格、角色和邀请状态，事务内再次核对相同快照。查询使用 JSON 参数，支持 200 人且每条语句不超过 D1 的 100 个绑定参数。

运行 `node --test tests/staff-platform-http.test.mjs` 可复测行为和 90 人性能基准。回归要求单人与 90 人预览的数据库读取次数相同，且本地 90 人预览低于 10 秒。开发机 Miniflare 实测约 31–99 毫秒、10 次读取（含操作者上下文）；这是本地基准，远端 D1 的耗时需要部署后在相同条件下比较。

`tests/e2e/staff-members.spec.mjs` 覆盖差异确认、权限隔离、单人新增、重复学号、任职编辑和部门维护，并输出 320/390/768/1440 像素下的人员详情截图。
