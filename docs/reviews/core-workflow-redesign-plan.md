# 核心业务流程与规则重构方案

业务基线 v1.2，2026-11-05。代码核对基准：`dev`，`f73ec74`。

本文整理本轮对话中的业务决定，核心业务讨论已收敛，供后续分阶段实施。已确认规则来自本轮对话；实施建议及默认处理由这些规则推导，不再逐项扩展边界问题。现有业务代码尚未按本方案改造，历史评审文档原样保留；其中与本轮决定不一致的建议，不作为本轮实施依据。

本轮范围修订：志愿时长复用现有核算方法，不重新设计计算规则。此前讨论的固定周额度、月度封顶、跨月结转、学期末清零及统一职级默认时长等新要求，均移出本次实施和验收范围。现有核算代码直接适配新流程的数据与身份规则，不保留旧流程，不建设兼容层或新旧双轨。

## 1. 定位与判断标准

系统定位为轻量级维修服务运营系统，以低操作成本实现预约容量控制、维修责任与历史追踪、排班考勤和志愿时长统计。

限制必须说明保护了什么具体业务结果。优先复用预约信息、登录身份、操作时间及状态变化；统计不另设一套维修人员填报任务。不以现有测试、页面、数据库约束或既有制度的存在，证明业务规则有必要保留。

重新设计业务，通过现有系统分阶段改造，不另起一套 V3。复用可靠的数据基础、对象级授权、审计和事务机制，直接修改受影响的接口及调用方，同时移除其中固化的旧业务限制。复用现有实现不等于保留旧流程或旧接口供兼容使用。

本轮聚焦高频流程与已经明确的例外，停止扩展低频边界场景。技术参数由开发按既有能力和合理默认处理，特殊情况优先通过已有登记、补记及更正解决，不再为每种情况增加配置、审批或新状态。

## 2. 已确认的维修服务规则

核心路径：**预约或现场登记 → 首次接收设备并留存外观照片 → 维修人员直接接单 → 结束本次服务 → 原故障续修或复发时建立关联新单。**

| 环节 | 目标规则 |
| --- | --- |
| 预约 | 线上预约继续严格控制名额。客户通过普通预约再次来修时，使用正常预约名额。预约时段用于分散预计到场人数，不等于现场排队顺序或必须在该时段内接单的限制。 |
| 当天到场 | 预约当天均可直接沿用原预约接单，不因早于或晚于所选时段要求改约、重新预约或恢复过期状态。不得在预约日内仅因时段结束或提前截止时间使预约失效；已取消、已结束工单不因日期相同自动恢复。 |
| 当天未到场 | 预约当天完全未到场，旧预约保留为过期、未到场记录。隔天再来通过新预约或现场登记办理，不算返修，也不为旧预约生成维修结果。 |
| 临时加人 | 允许工作人员根据现场余力登记未预约的客户，包括首次来修及关联返修；线上预约名额已满不阻止现场登记。记录现场登记来源、登记人和时间，线上预约的容量规则继续生效。 |
| 接待 | 维修人员可直接接单；办公室可以提前完善资料、拍照，人员协调可以在线下完成。保留必要的接收事实，不要求先经过线上分拣或分派。 |
| 接单条件 | 所有有效工作人员账号均可在工单访问范围内直接接单，不根据部门、职级、交流身份或单独的维修资格限制谁可以维修。取消一人只能有一张未完成工单的限制；不以当天排班、签到或正常值班时间作为接单、续修的前置条件。 |
| 设备资料 | 复用预约中的品牌、型号、故障和联系方式，有误才修改。未知型号可以留空；保修、液金等信息作为维修参考，不要求重复确认。 |
| 主修责任 | 接单人为当前主修。只记录主修与正式交接，不要求填报共同维修的协助人员。完善资料、上传照片不会改变主修。 |
| 跨日与交接 | 设备留在现场、尚未结束本次服务时，继续同一工单。可访问该工单的工作人员实际接到设备后即可确认接手，无须原主修在线确认或部长审批，也不再检查独立维修资格。自动记录交接前后人员和时间。 |
| 结束服务 | 结果为“已解决、部分解决、未解决、无需维修”。每次留一句处理说明；部分解决或未解决时写清剩余问题，不要求完整过程报告。结果与“服务已结束”分开表达。 |
| 结束后更正 | 在当前校区授权范围内，结束时的主修可以更正维修结果和说明，部长及以上可以代改。保留原值、修改人和修改时间，不改变历史接单及交接责任。 |
| 再次到访 | 客户取走设备后，本次服务结束。原故障继续处理或复发时建立新的关联返修工单；同一设备出现全新故障时按普通新单处理，历史照常可查。原单结果及历史继续保留，不因后来复发而改写。日期未知时不建立待排期、待联系或追踪安排的任务。工作人员可在线下协调时间。 |
| 历史与联系 | 普通维修人员可检索当前授权校区内的维修历史，包括他人主修的工单；查阅不依赖当天排班或签到。可查看单张工单的必要联系方式，访问自动留痕。该能力不等于开放批量联系方式导出。 |
| 客户查看维修记录 | 客户可查看维修结果；维修说明和操作历史仅供内部查看。不额外要求维修人员填写一份客户版说明。当前工单及历史、关联工单均遵守这一展示范围。 |

### 外观照片

照片用于保存首次接收时的外观证据，包括维修人员当时未注意到的问题，不能改为“只有发现损伤才拍”。

1. 本次服务首次接收设备时保留正、反面两张照片，接待人员或维修人员均可完成。
2. 照片随工单保存，维修人员接手时直接复用。
3. 同一工单跨日或换人不重复拍摄；出现新的外观变化可以补拍。
4. 设备被客户取走后再次送来，属于新的一次服务，需要重新记录当次外观；是否关联原单取决于是否为原故障续修或复发。

首次接收必须拍摄正、反面两张照片并尝试上传。上传超时后，页面直接显示“稍后补传”按钮；选择后可继续接单，并在该经办人的工单历史列表中标记“待传”。系统保存待传状态、所属工单及经办人。该按钮在上传超时后出现，不是初始页面上的免拍照选项。

经办人之后从历史中的“待传”记录进入，手动选择并上传首次接收时拍摄的原图；所需照片补齐后清除“待传”标记，未补齐则继续保留。补传不改变工单主修、维修结果或服务状态。

原图由经办人保存在手机或本地，页面提示保留原图供后续手动补传；不能用维修后的补拍冒充接收时的外观证据。不要求网页跨页面缓存、恢复图片，不实现后台自动重试、自动补传或上传任务队列。后续跨日、换人或补充说明均不触发重新拍摄要求。

### 返修关联入口

查找原单后可以发起关联服务；本次已经预约的，将该预约对应工单关联原单，不再重复建单；未预约直接到场的，从原单创建现场工单。普通接单时提示该客户已有历史维修记录，由工作人员查看并确认关联，不凭学号相同自动判定返修。

只有同一设备的原故障继续处理或复发，才关联为返修并纳入返修统计。同一设备的全新故障按普通新单处理，不因客户、设备相同或曾经来过就计为返修。未到场后重新登记也不计返修。

返修作为工单之间的关系，不作为第五种维修结果。返修工单本身仍然需要记录自己的处理结果。接单页面提供原单结果、说明和历史入口，不要求进入独立的售后排期模块。

### 自动留下的事实

系统记录接收、接单、交接、结束及修改的操作者和实际操作时间；字段修改保留前后值。联系方式访问保留访问人、时间和工单对象，不要求每次手填查阅理由。审计日志不重复存储明文联系方式。

主修责任统计只能说明谁接单、接手或结束服务，不应宣称覆盖所有实际协助人员的劳动，也不能作为出勤或志愿时长依据。

### 身份与管理范围

记录人员身份，供展示、追溯、管理范围和现有时长核算使用。谁来维修由现场实际情况决定，不再建立或保留独立的线上维修资格准入、审批或特殊授权流程。身份、部门或交流关系不作为能否接单和接手的门槛。时长核算直接读取新身份模型，不为旧报表保留旧资格或权限包判定链。

| 管理人员 | 已确认的管理范围 |
| --- | --- |
| 部长 | 按校区隔离，管理所负责校区内各部门的资料、排班调整和考勤补记，不再按本部门限制 |
| 站长、主席 | 可以管理全部校区的资料、排班调整和考勤补记 |

资料管理、排班调整和考勤补记采用同一管理范围，后台校验访问和修改并保留审计。上述业务管理范围不自动等同于受保护账号或系统权限配置的修改权。

## 3. 排班、考勤操作及志愿时长复用

### 排班

成员提供通常可用时间，后续默认沿用，每周只修改变化。未更新不阻止排班，也不标为“本周已确认”。临时变化只影响对应周；长期变化才更新通常可用时间。负责人处理缺口后发布排班，不强制全员每周重新填写问卷。

已发布排班允许调整：请假直接登记，无须先找到替班或等待批准；接替者确认后即可换班，无须部长重复审批。已经在线下协调好的，部长可以直接修改本校区排班，站长、主席可以调整全部校区。系统保留修改记录，并区分已请假与未请假未到岗。

### 考勤操作

保留现场签到码，部长及以上可以出示授权范围内的签到码。签到用于记录实际到岗，不作为维修操作的前置条件。默认发放时长不生成虚假的签到记录。

漏签可以由部长在本校区范围内补记，站长、主席可以处理全部校区的补记。补记保留操作者、真实操作时间及所补记的到岗事实，不能将补记操作时间冒充当时的现场签到时间。

本轮不根据已撤下的新时长方案，另行扩大签到资格或重定义有效出勤。维修接单与考勤解耦，已确定的签到码展示及补记管理范围照常落实；考勤记录按既有核算含义提供给报表。

### 志愿时长：复用算法，直接适配新流程

沿用现有周报、月报的计数方式、小时换算及现有核算参数的含义，不在本轮统一或重写核算算法，也不将此前讨论的新 4/16 小时方案强加给现有配置。月度封顶、跨月结余、学期末清零等不进入本次开发任务。

直接修改现有核算代码，使其读取新流程中的签到、任职身份、校区和服务日数据。负责人判定等输入按新身份模型处理，不保留旧权限包、维修资格或旧取数路径来维持报表运行；相关接口与页面同步修改，不增加一层把新数据伪装成旧流程数据的适配器。

历史签到、任职及报表事实继续保留；需要转换结构时一次性迁移到新模型，新旧数据随后由同一套新路径读取，不采用双读、双写或运行时回退到旧逻辑。维修工单数量和持续时间仍不替代实际考勤依据。

## 4. 重点删除、合并和保留的设计

以下是根据已确认目标提出的改造清单，具体接口和数据迁移随实施分批确定。

| 现有设计或候选功能 | 处置方向及根本理由 |
| --- | --- |
| 按部门、交流身份或特殊授权判定维修资格 | 删除线上维修准入限制及为此设置的配置、审批入口。身份保留为人员信息，接单和实际交接自动记录责任；管理范围仍单独按业务需要控制。 |
| 一人一单、待接手单占用人员、维修未结束不能离岗 | 删除相应硬限制。主修与操作历史已经能够追踪责任；人员可能跨日、并行处理设备。不能连带保留依赖“一人一单”的占用机制。 |
| 接单必须签到、处于在岗状态及工作窗口 | 删除考勤前置阻断。人员身份、工单责任和实际出勤分别记录，维修操作不会自动生成考勤。 |
| 同日跨时段接单要求改约，或预约日内提前失效 | 取消。预约当天均可沿用原单，保留原预约时段和实际接收、开修时间。 |
| 把线上预约容量作为现场接待总量的硬上限 | 不采用。线上预约严格限额，现场临时加人登记并记录来源；现场登记不应通过修改放号容量或冒充线上预约实现。 |
| 队列位置、队首限制、越序说明、离队重排 | 按本轮现场描述，建议从日常流程移除。现场没有可靠的严格顺序，人员呼叫与等候可以线下处理。预约容量控制继续保留。 |
| 预分派、待接手、退回分派、撤回分派 | 以直接接单取代线上分派链。保留已经开始维修后的实际交接及其历史。 |
| 每次接手重新拍照、限定照片必须由当前接单者上传 | 首次接收保留正、反面两张照片，全单复用。证据归属于设备的本次服务，上传人不必是主修。 |
| 已拍照但上传超时仍阻止接单 | 超时后显示“稍后补传”，选择后可继续接单，经办人的工单历史标记“待传”；之后由本人从该记录手动补传原图，不建立后台自动重试或补传机制。 |
| 重填设备资料、未知型号阻断、重复保修或液金确认 | 复用预约信息并按需更正。缺少参考信息不等于无法提供维修服务。 |
| 返修申请后再审批、排期、维护后续联系任务 | 从新流程移除，以实际预约或到场时建立关联替代。用户已明确不要求系统管理后续安排。现存申请需妥善转换，历史保留。 |
| 强制每周问卷、重复确认、请假及换班层层审批 | 改为常规可用时间、按周例外、直接登记请假及接替确认。负责人处理真实缺口。 |
| 既有周报、月报计时方式及核算选项 | 复用现有计算方法与参数含义，直接改造取数和身份判断以使用新流程；本次不统一算法、不新增月度封顶或跨月结转，也不保留旧接口作为兼容入口。 |
| 签退、暂离、返回与维修业务联动 | 解除这些状态对接单、续修的阻断，以及未完成维修对离岗的阻断。本轮不再以固定周额度为理由重设计考勤状态或删除核算所需记录。 |
| 协助人员填报、完整维修日志、独立统计填报 | 不新增。保留主修、交接、结果和简短说明，统计复用已有数据。 |
| 后端对象级授权、校区范围、附件边界、审计、并发保护 | 保留并适配新规则。简化入口不应让越权访问、重复接手或覆盖历史成为可能。 |

## 5. 最小业务模型建议

沿用现有预约与工单基础：正常维修主要表达“待接单、维修中、服务已结束”，取消和预约过期保留为预约处置。首次接收、照片、当前主修及交接作为事实记录，无需再建立在线队列和分派状态链。

服务结束不等于维修成功。四种结果独立于主状态；返修关联也独立于本次结果。留机跨日不是一次新预约，人员交接不是一次新服务。

排班表示谁应该来，签到表示谁实际来，志愿时长由现有核算方法根据新流程的数据计算。算法产生的默认时长不能混为真实到岗人数。

预约当天可以直接接单，原预约时段与实际服务时间分别保留；临时加人沿用现场登记入口，不另设超额审批状态。当日完全未到场的预约跨日后保留为过期记录，后续来访使用新预约或现场登记。状态命名和历史映射复用现有模型，不因采用上述最小模型而丢弃旧状态记录。

## 6. 实施默认与基础配置

核心业务没有剩余的前置确认问题。以下内容作为实施安排处理，不扩展为新的业务需求，也不宣称每项技术默认都经用户逐条确认。

| 事项 | 处理方式 |
| --- | --- |
| 签到依据 | 沿用有效出勤的既有含义，不再从已移出范围的新周额度方案推导新的签到资格规则。维修权限放开不会自动生成签到或时长。 |
| 上传与签到参数 | 上传超时阈值由开发采用合理固定值；超时显示“稍后补传”，历史标记“待传”，由经办人手动补传。签到码有效期优先复用现有机制，不为这些参数建设新的通用配置页面。 |
| 志愿时长取数 | 在现有计算代码内直接改用新模型的字段及身份判定，保留原有计数、换算和归周归月方法。无需为跨月结转或学期清零新增字段、配置和任务。 |
| 任职和低频异常 | 使用真实任职数据，不新增时长折算制度。保留取消、暂停服务等必要能力，特殊情况优先用登记、补记和更正处理；与新主流程冲突的旧限制按新规则调整。 |
| 数据与接口改造 | 直接修改原实现、接口和调用页面；每个业务批次切换时同步停用对应旧路径。保留历史事实并按需一次性迁移，不设兼容接口、旧参数别名或新旧双轨。具体字段、迁移和代码拆分不再转为业务问卷。 |

## 7. 分阶段实施与业务验证

1. **按基线拆分改造任务。** 业务范围以本文为准，梳理现有字段、接口和约束；区分保留、修改和移除项，更新相冲突的需求说明，暂缓一般性功能扩张，不再以继续补齐边界场景作为实施前提。
2. **先改维修主流程。** 按接收与接单、跨日交接、结束与关联返修、历史查询依次拆分。每个改动贯通后端、界面及必要数据迁移，切换时同步移除对应旧入口和旧路径，保留必要的权限、事务、附件与审计保护。
3. **再改排班与考勤操作。** 落实常规可用时间与每周例外，简化请假换班及管理范围。现有时长核算代码直接改用新流程数据，继续执行原计算方法；不新增周额度、月结算或学期截止系统。
4. **真实使用验证与清理。** 用代表性接待和维修人员完成实际场景，清理残留无用分支。旧队列、待分派和待返修安排中的记录在对应批次切换时一次性转入新流程并保留历史，不让旧办理流程继续并行运行。

原始维修、签到、照片和审计历史继续保留。旧“未修复”记录不能凭空细分成“部分解决”或“未解决”；历史没有协助人员或经手记录时，不补造事实。历史报表不按本轮已撤下的新时长方案追溯重算；历史保留通过数据迁移和统一新模型实现，不依赖旧流程兼容分支。

业务验证重点是：正常预约并发下仍不超容量；有效工作人员可在工单访问范围内不经维修资格审核、签到或分派直接接单；多单、跨日、换人不丢照片及责任历史；结束后再次来访正确关联且不重复建单；授权校区内可查历史和联系，越权访问被阻止；资料、排班调整及考勤补记均按部长本校区、站长和主席全部校区的范围执行；现有计数与小时换算方法能正确使用新流程数据，身份按新模型判断，维修操作不自动生成考勤或时长。移出范围的新时长规则不作为验收要求。

预约当天跨时段接单不要求改约或恢复过期；线上预约满额时可由工作人员现场加人登记，来源可追溯，同时客户线上预约仍不能突破名额。未到场的旧预约过期保留，隔天到场新登记不计返修；同设备新故障不计返修，原故障续修或复发才关联统计。

照片在首次接收时拍摄，上传超时后显示“稍后补传”；选择后能继续接单，经办人的工单历史中可看到“待传”并手动补传。所需照片补齐后标记消失，未补齐时仍保留；不得自动发起后台重试或补传请求。原图由经办人自行留存，网页不承担跨页面自动恢复。客户页面及接口不得返回内部维修说明和操作历史，包括历史及关联工单中的嵌套内容。

记录完成率、返修关联准确性、接单与结束耗时、重复填报次数以及线下绕过系统的情况，用于判断改造效果。代码检查随变更服务于这些新规则，不要求旧业务断言原样保留。
