# 维修排班求解验证

对应规格第 22、31、37.10 章；算法 `bounded-flow-campus-v3`，rosters 模块 1.4.0；未修改数据库迁移。

## 目标与约束

先满足可参加关系、负责人覆盖、每人每周一次与锁定分配，再最大化安排人数。班次没有人数上限，因此在覆盖可行时，可以安排所有至少有一个可参加班次且未锁定的成员。

跨校区均衡采用各校区人数差之和（校区等权），再最小化各校区每日人数相对本校区平均值的平方偏差之和。不会为了让全局人数相同而搬动本来人数较多的校区。相同目标值按稳定成员序、校区序和班次序确定性选择。锁定固定人员与班次，符合资格的锁定人员仍可担任负责人。

带下界流同时约束人员选择、负责人通道、班次人数和校区总人数。对校区总人数与人数区间逐层求解；总人数固定后，最小平方人数费用等价于最小平方偏差。只有完成该层搜索且通过独立校验才返回 `optimal`。默认预算为 8,000,000 次边扫描/搜索操作；耗尽时保留已有解，或保留诊断草稿，明确标记 `feasible` / `needs_review`。发布始终重新读取资格和覆盖事实。

## 可复现证据

- `node --test tests/roster-optimizer.test.mjs`：7 人反例由 3/1/2/1 改为 2/2/2/1；单日集中、空可用时间、负责人稀缺、锁定、批准请假、输入重排、预算耗尽，以及 90 组固定种子小输入与独立全枚举对照。
- 同一测试包含 200 人、两校区、四工作日的全可用和受限时间输入。本机 Windows / Node 25 测得约 10–20ms，工作量分别为 1,628,959 / 1,193,135；全员安排且独立校验通过。全可用时每校区 25/25/25/25；受限时为 19/19/19/18 与 32/31/31/31，均已证明本模型目标最优。耗时是本机测量，不是生产容量承诺。
- `tests/staff-platform-http.test.mjs`：真实 Worker/D1 保存与恢复求解状态、指标、算法版本和实际可参加关系快照；输入变化即使不影响现有安排的合法性，也会标记需要重新核对；人工编辑清除旧优化结论；不能用伪造校验结果发布，资格变化阻止发布。
- `tests/e2e/roster-flow.spec.mjs`：管理页展示实际人数差、诊断及调整状态，刷新恢复、锁定重新生成和 320/390/1440px 布局。

仍待完成：部门范围排班、完整角色/时点矩阵及规划清单中的其他未验收项。此证据不代表人员平台整体完成。
