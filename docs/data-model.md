# 新数据模型与阶段边界

本版本仅支持空数据库上应用 `0001_initial.sql`。旧开发数据和迁移不兼容，重建步骤须显式执行；运行时不迁移或初始化数据。

| 实体 | 职责与约束 |
|---|---|
| `staff_accounts` | 正式工作人员；角色仅 technician/admin/superadmin，状态 enabled/disabled；home_campus 只描述所属校区；受保护 root 必须启用且为 superadmin |
| `staff_campus_grants` | 独立校区授权；所属校区不自动授予数据访问权；复合主键防止重复授权 |
| `staff_whitelist` | 学号资格、预期角色、可选预期姓名和 open/revoked/activated 状态；不会保存密码或创建登录身份 |
| `whitelist_campus_grants` | 审批后授予的校区；申请人不能自行提升角色或扩大授权 |
| `activation_requests` | 申请资料、密码哈希、申请回执哈希及审核记录；同学号最多一个待审、一个通过申请；拒绝保留记录并允许重新申请 |
| `appointments` | 业务编号用于展示；256 位随机访问凭证独立生成，只保存 SHA-256；服务端不返回哈希或再次返回原凭证 |
| `credential_recoveries` | 人工核验后的凭证重签记录，保存操作人、原因和时间；不保存凭证明文 |
| 附件与额度 | R2 私有对象、D1 元数据与预留额度；过期、失败补偿和容量原子保护保留 |

所有正式账号、待审申请和学生预约身份相互独立。学生继续免注册，不存在 student 登录角色。停用账号保留历史接单关联；不提供删除账号 API。账号和预约通过 revision 防止并发覆盖，校区授权更新与账号 revision 在同一 D1 batch 中提交。

阶段 1 建立结构、移除旧角色并适配现有代码。阶段 2 将所有学生敏感接口切换到访问凭证，并实现浏览器保存和人工恢复。阶段 3 集中执行校区与接单权限。阶段 4 开放白名单申请及审核，正式账号仅由通过审核的申请原子创建。阶段 5 完成 UI 和浏览器验收；阶段 6 仅准备可审计发布方案，远程重建与发布须另行明确批准。

无短信或邮件时，学号不能证明身份。待审申请不能登录，管理员必须通过线下认识、部员名册或当面核验申请人；遇到抢占待审申请，拒绝后让本人重新申请。不得仅因学号存在于白名单就自动批准。凭证遗失也须人工核验后重签，并立即使旧凭证失效。
