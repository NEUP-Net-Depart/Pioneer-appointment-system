# 值班编排与空闲

业务基线为 `docs/requirements.md` v1.2。

`shared/duty.js` 集中维修、办公19:00–21:00、周一至周四和签到18:30–21:30常量，无时段配置页面。成员通过 `GET/PUT /api/me/availability` 保存通常空闲（`weekStart: ""`）或指定周一的例外。沿用 `windows`（`weekday` 1–4、`campusId`、`startAt`、`endAt`）结构，界面只提供四天的整班勾选，接口也拒绝周五至周日。新保存必须在授权校区至少覆盖一天19:00–21:00，空数组及仅部分覆盖返回400；旧空数组仍按空闲缺失读取，旧周末窗口不进入填报界面，读取不修改原行。`useUsual: true` 仅在通常安排含至少一天有效空闲时保存 JSON `null`，保留例外并递增 `revision`；后续修改仍携带该版本。`source/effectiveWindows` 表达实际安排，不生成每周确认记录，响应的 `participates/needsAvailability` 给出参与资格和有效空闲缺失状态。

个人空闲填报与自动候选仅针对有效硬件部主要任职部员、维修事务部员；交流维修本身不产生候选。界面统一显示“空闲时间”，按授权校区填写，不切换值班类型。任何有效的部长（含副）及以上任职均不参与，无论该任职是否主要任职；退休老登也不参与。所有无填报资格的成员均显示“值班统计”区和“不参与值班统计”，不提供填报按钮，后端拒绝空闲提交。负责人及退休老登同时不能新增排班与接替；管理排班权限保持独立。

空闲接口不再要求 `dutyType`，旧调用携带的类型忽略。复用 `member_availability`，不迁移、不新增表：通常空闲及每周例外各自从历史两类型记录中选择 `updated_at` 最新的一条，同一时间以 `duty_type DESC` 稳定排序。最新例外的空数组表示本周无空闲，JSON `null` 表示恢复通常安排，不回退到更旧的另一类型例外。保存更新对应的已有行，首次填报使用 `repair` 存储槽；版本守卫检查当前最新行的类型和版本，旧版本不能覆盖。两类班表、建议和发布警示共用该有效空闲。

`GET /api/rosters/campus-week?weekStart&campusId` 返回两类班表、人员、统一空闲、暂停日和 `sourceVersion`，为兼容管理端，两类型的 `availability` 字段返回相同窗口。人员同时返回所属校区、授权校区和有效任职，以便手动选人显示真实部门与职位。`POST /api/rosters/week/suggestions` 接收周一、校区及需保留的 `assignments`，返回草稿、缺口、未安排原因、优化结果与输入版本，不写班表。默认保留符合班次资格的已发布项，前端重新生成时提交发布及手动项，排除上次自动建议。兼具硬件部部员与维修事务任职的候选自动优先排办公，保留的手动班次不受自动优先策略影响。

办公自动建议只从已填且当天在本校区整班空闲的维修事务任职部员中选人，每个非暂停日最多新增至一人，无人可排留空并提醒，不强制覆盖每天或安排每位办公候选。可在本人空闲日轮值，优先分散到不同成员；避免同日其他校区或岗位冲突，已有办公安排不自动补人。兼具硬件部资格的成员优先排办公，但仍每周合计一天，未排到办公时进入维修安排。维修比较多种均衡配额，以最小费用匹配为每个尚未安排的硬件部员分配一天；未填空闲也进入维修安排并计为空闲冲突。先保证完整安排及维修每日人数差不超过2，再最小化冲突，同等冲突时优先减少缺岗并均衡人数。办公及每日合计不套用维修均衡约束。历史外校区班次只阻挡重叠时段，不计入所属校区的每周名额。保留的手动班次、任职范围或全部暂停使条件不可同时满足时，返回 `optimization.complete/balanced` 并提示。

排班、个人值班、签到提醒和按周考勤导出使用 `dutyWeekKey`，周一为首日、周日为末日。排班周选择器显式使用周一口径。原 `rosterWeekKey/calendarWeekRange` 保留供预约概览、服务日配置和原周日历使用；具体日期与空闲星期值不转换，历史排班的周一键不改写，不新增数据库迁移。

`PUT /api/rosters/campus-week` 接收 `{weekStart,campusId,sourceVersion,requestId,rosters:[{dutyType,revision,assignments}]}`，维修、办公必须同时提交。版本、目标人员有效性、班次资格、校区授权、暂停日、其他校区与两类班次的时间冲突均在发布时校验。普通成员手动重复、未填空闲仅警示并进入审计，无每日人数门槛。未变更的行保持 ID、特殊时段和接替历史。主动替换新增固定时段行，旧行归档，取消失效的待确认接替邀请。发布还幂等准备每日共用值班签到场次，不生成签到。事务包含两类班表、场次、审计与回执，失败不留半份发布。

`dutyPlanningReview` 在建议、前端草稿和发布时共用核对逻辑。`gaps` 按日期和类型分别列出未覆盖班次；`unassigned` 只核对有每周排班要求的硬件部员，包含成员、岗位、`reasonCode/reason`。未使用的普通办公候选不作为遗漏。前端依据当前草稿持续计算；未填的硬件部员不会因无可选日期而从提示中消失。

暂停维修当天仅显示原定值班人员。原班次只读，发布时原样保留，不计入缺岗、重叠和每周排班名额，也不参与调岗。建议接口的 `excluded` 接收当前草稿中手动排除的人员、日期和岗位组合。排班页刷新时合并可兼容的草稿与最新班表，对同一班次的不同改动需选定后再发布。人员的外校区占用信息用于提前检查重叠，只有同时具备相应校区排班管理权限时才返回校区和岗位。

自动建议、手动选人、发布及接替均要求成员所属校区与班次校区一致，校区访问授权不能替代所属校区。历史跨校区班次在原班表中保留，管理员可移除。班次来源记录在 `duty_assignments.assignment_source`，新增自动建议保存为 `auto`，手动、移动、交换或接替保存为 `manual`。迁移前缺少来源的班次显示为「原排班」。

系统不提供请假流程。成员线下通过 QQ 找负责人处理请假，负责人按沟通结果修改班表；双方自助调岗无需负责人参与。0056删除 `roster_leaves` 及请假专属审计、回执，移除请假接口、服务和状态字段，班次覆盖、考勤、人数统计均直接读取有效班次。维修与办公缺岗始终分别提示，允许核对后继续发布。

维修班次仅限班次当天有效的硬件部部员或交流维修成员，硬件部部员优先显示。办公班次仅限班次当天具有有效维修事务任职的成员，基础事务站部员（办公室、美工部、推广部）优先显示。选人、移动、交换、发布及接替均按目标班次校验资格。历史不合规班次保留在已发布班表中，生成建议时从草稿剔除，重新发布前须处理。空闲不符及每周重复安排作为可发布的提示。

`GET/PUT /api/rosters/week` 继续支持单类型读取和发布，使用同一固定时段校验与事务写入。普通工作人员只读本人班次，管理范围与成员管理一致。

`GET /api/me/roster` 返回本人指定周班次与服务端 `canRequestCover`，`upcoming=1` 返回从今日起最近30个非暂停班次，用于今日和下次提醒。`cover-candidates` 列出具备该班次资格的本校区成员。`cover` 由原值班成员创建接替邀请，`GET /api/rosters/covers` 查询本人邀请，`POST /api/rosters/covers/:id/response` 由接替者确认或拒绝、发起者撤回。发起和同意都要求 `businessDate > dateKey()`，北京时间值班当天零点起禁止，服务与写入守卫均检查日期和班次资格。旧双班互换校验双方各自接替的班次，以较早日期为截止。过期的待确认邀请投影为 `expired`，不计入待办，不新增存储状态。对方同意直接原子更新已发布班表，无负责人审批或重新发布步骤。系统保留班次 ID、原发布时间，递增班次及班表版本，失效其他冲突邀请，并刷新个人班次、今日名单和管理端班表。已成功操作的相同请求在过期后重试仍返回原回执。

`roster_weeks` 是校区/周/类型的并发版本；`duty_assignments` 保留全部历史 ID，`active` 标记有效班次；`member_availability` 保存通常时间与例外；`roster_covers` 保存双方邀请与确认。修改、审计、操作回执在同一 D1 batch 中提交。实际签到在 `attendance_records`，维修接单与这些记录互不作为前置。

0048的非请假工作流归档保持不变；0050追加关联班次与成员的 `attendance_reviews`，不改写原班次和签到。核查及直接到场见 [签到策略](attendance-policies.md)。
