# 到场接待、排队与维修分派（Issue #69）

## 已确认的业务规则

1. 办公接待人员或具有相应权限的维修负责人扫描客户维修码，核验设备并拍摄正反面照片。到岗签到码仍只用于工作人员考勤。
2. 完成接待后，工单按到场时间进入所属校区的现场队列。接待人员手动选择空闲且符合资格的维修／交流人员；候选显示身份及当天已接、已完成工单数，不自动选人。
3. 分派后为“待接手”，立即占用接手成员的一单名额。维修开始时间留空，确认接手才开始维修。其他人员不能抢接。
4. 接手人员可检查并更正核验信息、替换任一设备照片；保留的照片必须属于本工单且已由接待核验。退回队列必须填写原因，保留原到场顺序。
5. 无空闲人员时保留排队。跳过队首需填写原因；检查在写入事务中再次执行。现场管理也可填写原因撤回待接手分派。
6. 普通维修及交流人员保留直接核验接单，无需说明原因；仍需资格、校区、签到、在岗、工作窗口和一人一单检查。
7. 已接待的排队／待接手工单不自动过期，跨日显示在接待台。联系客户后可继续处理、改约或取消。改约沿用当前开放日期、时段、容量、暂停和重复预约限制，保留原单号与用户查询凭证；重新到场后重新接待。
8. 校区暂停维修后，禁止新增接待、分派和开始维修；已到场工单仍可退回、撤回、取消，或改约至其他开放日期。当前窗口没有开放时段时明确提示并保留队列。

## 状态与数据

预约五种主状态保持不变：`booked / in_progress / completed / cancelled / expired`。
新增 `repair_receptions` 保存现场阶段：`queued / assigned / started / closed`。
预约仍为 `booked` 时，只有 `queued / assigned` 替换展示状态。改约关闭旧的现场流程后仍显示“已预约”。

`0039_reception_dispatch.sql` 在 dev 与 Staff Staging 两条迁移链中追加相同内容，不改旧迁移，不重写历史预约。
已有工单没有接待记录时继续使用原核验接单流程。迁移按既有接待或转派角色授权复制接待／分派权限，并保留原校区、条件、有效期及成员绑定范围。

待接手按稳定 `memberId` 建部分唯一索引；数据库同时阻止与进行中维修冲突、抢接他人分派、暂停日分派及带着待接手工单离岗。
工单 revision、人员签到 revision、授权版本、值班窗口、审计和请求回执在同一 D1 batch 中校验或写入。审计／回执失败会回滚业务写入。
网络响应丢失时前端使用原请求编号和原 revision 重试一次，再查询实际工单；权限／业务冲突不自动重试。

`repair.receive` 负责接待，`repair.dispatch` 负责分派、撤回、改约及取消；普通维修人员只可退回本人的待接手工单。所有命令独立校验权限，入口隐藏不作为安全边界。
接待记录按当前授权校区及完整对象范围可追溯，用户端不返回接待账号、分派成员编号等内部信息。
工作量按当天接单／转派及完成审计分别统计；没有相应审计的历史记录用既有开始／完成事实补足，避免转派后把原接单人工作量抹去。

## 接口与页面入口

- `POST /api/appointments/:id/reception`：`receive / assign / return / withdraw / reschedule / cancel`，携带 `revision` 和 `requestId`。
- `GET /api/field/appointments/:id/dispatch-candidates`：返回当前可接单人员。
- `GET /api/appointments/:id/reception-options`：返回可改约的开放日期和时段，提交时再次校验。
- 既有 `/api/field/home`、`board`、工单详情、预约记录、编号搜索及用户预约页面复用现场阶段投影。
- 接待台 → 扫客户维修码或打开预约 → 现场核验 → 现场队列 → 选择人员 → 分派。
- 维修工作台 → 查看待接手工单 → 核对或更正 → 确认开始／填写原因退回 → 维修结果确认。
