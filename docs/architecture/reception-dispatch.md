# 到场接待、排队与维修分派（Issue #69）

## 已确认的业务规则

1. 办公接待人员或具有相应权限的维修负责人扫描客户维修码，核验设备并拍摄正反面照片。到岗签到码仍只用于工作人员考勤。
2. 完成接待后，工单按到场时间进入所属校区的现场队列。接待人员手动选择空闲且符合资格的维修／交流人员；候选显示身份及当天已接、已完成工单数，不自动选人。
3. 分派后仍归入“排队中”，显示接手人员及“等待确认”。立即占用接手成员的一单名额，维修开始时间留空；维修人员当面核对客户和设备并确认后才开始维修。其他人员不能抢接。
4. 接手人员可检查并更正核验信息、替换任一设备照片；保留的照片必须属于本工单且已由接待核验。退回队列必须填写原因，保留原到场顺序。
5. 无空闲人员时保留排队。跳过队首需填写原因；检查在写入事务中再次执行。获授权的负责人也可填写原因撤回待接手分派。
6. 办公人员未到场时，具有接待／分派授权且在授权校区签到的维修负责人可代接待、核验、发号和分派。普通维修及交流人员保留直接核验接单，但已有队列时只能接未分派的队首；仍需资格、校区、签到、在岗、工作窗口和一人一单检查。检查在提交事务内再次执行，不能绕过队列。
7. 已接待的排队／待接手工单不自动过期，跨日显示在现场工作台。联系客户后可继续处理、改约或取消。改约沿用当前开放日期、时段、容量、暂停和重复预约限制，保留原单号与用户查询凭证；重新到场后重新接待。
8. 校区暂停维修后，禁止新增接待、分派和开始维修；已到场工单仍可退回、撤回、取消，或改约至其他开放日期。当前窗口没有开放时段时明确提示并保留队列。
9. 客户可凭私密预约凭证退出排队，接待或负责人也可填写原因标记离队。离队保留预约和原过期时间，释放已分派的维修人员；再次到场须重新核验拍照，取得新号码并排至队尾。退出排队与取消预约分别确认。
10. 叫号后暂时找不到客户时保留原位置；接待或负责人填写越序原因后可先分派后面的客户。维修人员自行接单不能跳过队首。
11. 每校区每日独立发放不重复的到场号码；离队、取消或删除不会复用号码。号码是稳定凭据，实时排位会随接单、离队而改变；等待维修人员确认的工单仍计入等待人数，但不阻塞其他已排队工单的正常分派。

## 状态与数据

预约五种主状态保持不变：`booked / in_progress / completed / cancelled / expired`。
新增 `repair_receptions` 保存现场阶段：`queued / assigned / started / closed`。
预约仍为 `booked` 时，只有 `queued / assigned` 替换展示状态。改约关闭旧的现场流程后仍显示“已预约”。

`0039_reception_dispatch.sql` 在 dev 与 Staff Staging 两条迁移链中追加相同内容，不改旧迁移，不重写历史预约。
已有工单没有接待记录时继续使用原核验接单流程。迁移按既有接待或转派角色授权复制接待／分派权限，并保留原校区、条件、有效期及成员绑定范围。

`0040_reception_queue.sql` 在两条迁移链追加到场号码、每日计数器和离队时间。已有接待按校区、日期、接待时间补发号码，不修改原预约。计数器独立于工单保存，保证删除工单后不重用号码；排位、队首和提交检查使用同一排序规则，时间相同以号码区分。新增接待、发号、设备核验、审计和回执原子提交，失败不消耗号码。

待接手按稳定 `memberId` 建部分唯一索引；数据库同时阻止与进行中维修冲突、抢接他人分派、暂停日分派及带着待接手工单离岗。
工单 revision、人员签到 revision、授权版本、值班窗口、审计和请求回执在同一 D1 batch 中校验或写入。审计／回执失败会回滚业务写入。
网络响应丢失时前端使用原请求编号和原 revision 重试一次，再查询实际工单；权限／业务冲突不自动重试。

`repair.receive` 负责接待，`repair.dispatch` 负责分派、撤回、改约及取消；普通维修人员只可退回本人的待接手工单。所有命令独立校验权限，入口隐藏不作为安全边界。
接待记录按当前授权校区及完整对象范围可追溯，用户端不返回接待账号、分派成员编号等内部信息。
工作量按当天接单／转派及完成审计分别统计；没有相应审计的历史记录用既有开始／完成事实补足，避免转派后把原接单人工作量抹去。

## 接口与页面入口

- `POST /api/appointments/:id/reception`：`receive / assign / return / withdraw / leave / reschedule / cancel`，携带 `revision` 和 `requestId`。
- `POST /api/appointments/:id/queue-exit`：客户凭 `X-Appointment-Token` 私密凭证退出，携带 `revision` 和 `requestId`。提交时重新校验凭证；重复回执不会退出后来重新加入的队列。
- `GET /api/field/appointments/:id/dispatch-candidates`：返回当前可接单人员。
- `GET /api/appointments/:id/reception-options`：返回可改约的开放日期和时段，提交时再次校验。
- 既有 `/api/field/home`、`board`、工单详情、预约记录、编号搜索及用户预约页面复用现场阶段投影。
- 现场工作台 → 扫客户维修码或打开预约 → 现场核验 → 现场队列 → 选择人员 → 分派。
- 维修工作台 → 查看待接手工单 → 核对或更正 → 确认开始／填写原因退回 → 维修结果确认。
- 用户“我的预约” → 查看到场号码、实时排位及前方人数 → 刷新排位／退出排队。页面可见时每 30 秒刷新，隐藏时暂停；排位更新保留已打开的退出确认及键盘焦点。
- 新登记客户可在现场详情展开“让客户在手机上查看排队”，扫描私人查询二维码。它与工作人员扫描的客户维修码分开展示。凭证复用既有加密登记回执，仅向具有相应资料权限的登记人提供，凭证轮换后不恢复旧凭证；旧登记没有回执时不强行生成新凭证。

## 统一现场入口

接待和负责人协调共用“现场工作台”（desk）。按当前校区的有效权限显示客户核验、登记、签到码、分派和转派；普通维修人员不因入口合并获得现场管理权限。历史 operations 场景和保存状态归一到 desk，实际命令仍独立校验。仅保留顶部概览卡作为工单和空闲人员筛选入口，移除列表内重复筛选按钮；再次点击取消选中。

现场概览只保留“未到场 n/m → 排队中 → 维修中 → 空闲中”四卡。m 为今日非取消的实际预约工单数（含现场登记，不是容量）；n 为其中尚未接待、未离队的已预约工单数。跨日排队和进行中维修保留在现场列表。排队中包含等待分派及已分派等待确认；空闲中只统计实际可接单成员。卡片与列表筛选共用现场投影；列表标题随筛选变化，通过“显示全部”恢复列表。

## 与返修流程集成

历史工单按预约日期执行资料权限；存在接待记录不授予当日接待人员历史客户访问权。跨日排队与维修仅保留现场摘要及当前处理能力，姓名搜索和列表统计遵循同样的范围。取消、离队或改约使工单超出当前详情权限时，命令及重试回执仅返回处理结果，页面返回工作台。

普通改约只列出尚有容量的有效半小时时段；返修单保留 `onsite / repair_followup`，可以改到已满但仍开放的时段。两者都重新保存目标日期地点快照，并在提交时检查停修和排期。容量竞争继续由数据库约束裁决。

客户使用原工单私人链接查看后续返修排号和实时排位；`POST /api/appointments/:id/repair-followups/:followupId/queue-exit` 只接受该凭证工单的后续返修关系。事务重新核验凭证与关系，轮换凭证后旧链接失效；旧离队回执不会使重新到场的客户再次离队。多轮返修的维修码沿相同后续关系解析。查询原工单时同步处理整条维修链中未到场或已离队工单的到期状态。

新增 API 与浏览器回归覆盖历史范围、姓名搜索计数、返修满额改约、地点快照、父单凭证离队、凭证轮换、多轮返修，以及重复离队和重新到场。
