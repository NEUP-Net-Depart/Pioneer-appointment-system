# 授权与字段范围

授权判断单位是 `permissionCode + scope + conditions + validity`。`src/modules/authorization/conditions.js` 注册类型化条件，`createAuthorizer()` 对多个完整授权项取并集、对不同范围维度取交集，并返回 `matchedGrantIds`、`reasonCode`、范围解释和 `authVersion`。

列表、详情、搜索、导出和附件下载应使用同一授权结果。页面按钮只能把授权结果作为提示，写入仍由服务端在最新对象版本和授权版本下重新判断。角色、成员角色绑定变更会增加账号 `token_version` / `auth_version`，使旧会话失效。

权限目录以代码 manifest 和 `permission_definitions` 的版本化投影为准。角色是运行期配置，最高管理员可以为已登记权限设置校区、部门、对象和条件范围。联系方式、账号授权、导出和删除权限标记为敏感字段。

## 成员目录与条件参数

成员列表、搜索、详情、资料变更和任职变更使用同一个授权器：每个候选成员携带成员 ID、所属校区及当前有效部门，逐条匹配完整授权。不同角色的校区和部门不能拆开重组，过期授权及未来任职不参与当前访问。校区范围还收敛到当前账号的适用校区授权。

目录按姓名与 memberId 组成稳定排序键，每页返回最多 100 个可见成员。服务端分批扫描候选及有效任职，过滤后填满页面；对外游标仅包含最后一个已返回成员，不编码被过滤人员的信息。每条批量任职 SQL 保持在 D1 的 100 个参数限制内。React 页面支持继续加载、去重、取消旧请求及忽略过期响应。

`GET /api/permissions` 除权限目录外返回 `conditionProviders`，包含 code、version、说明与 parameterSchema。保存角色和执行授权均验证注册条件、版本与参数类型；未知配置不授予权限。当日岗位按具体校区、业务日、岗位类型与工作类型匹配，不能用笼统的 todayDuty 标记替代；任职和工作资格采用左闭右开的有效区间。

账号管理与激活审批由 `accounts.manage` 及其校区范围授权，基础类型为 technician 的成员也可执行明确授予的管理操作。基础账号类型仅保留最高管理员、受保护账号及管理员账号的身份保护，不再决定普通业务能力或缩窄预约范围。

预约列表将完整授权投影为 D1 条件，包括校区、归属成员、对象 ID 和当日岗位日期。姓名／学号搜索仅匹配拥有 `customer.identity.read` 的记录；联系方式只在授权后解密。查询、状态分面和总计采用同一可见范围，状态分面忽略当前状态选择；统计数量独立于当前页。

`GET /api/appointments` 默认每页 200 条，上限 200；React 每页 100 条。`nextCursor` 为不透明续页标记，组合排序字段后追加稳定键，后续请求须保留筛选及排序。新增排序或授权条件时必须同时更新数据库投影和与授权引擎对照的测试；未支持的条件拒绝列表授权。0032 为两个迁移历史追加校区分页和分面索引，原迁移不变。
