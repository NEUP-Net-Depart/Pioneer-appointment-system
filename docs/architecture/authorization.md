# 授权与字段范围

授权单位为 `permissionCode + scope + conditions + validity`。`src/modules/authorization/conditions.js` 注册类型化条件；`createAuthorizer()` 对完整授权项取并集、对单项的范围维度取交集，返回 `matchedGrantIds`、`reasonCode`、范围解释及 `authVersion`。

列表、详情、搜索、导出和附件使用同一授权结果。前端按钮只反映权限，写入由服务端结合最新对象版本与授权重新校验。成员、角色及绑定变化更新 `token_version` / `auth_version`，旧会话失效。

权限目录由 manifest 和 `permission_definitions` 的版本化投影定义，角色在运行期配置。校区、部门、对象、条件和有效期共同约束授权；联系方式、账号管理、导出及删除能力按敏感权限控制。

## 成员目录与条件

成员列表、搜索、详情、资料及任职变更逐条匹配候选成员的 ID、校区和当前有效部门。不同授权的校区和部门不可拆开重组，过期授权及未来任职不参与当前访问，校区同时收敛到当前账号适用范围。

目录按姓名与 memberId 稳定排序，每页最多 100 个可见成员。服务端分批扫描并过滤填满页面，游标只包含最后一个已返回成员；批量任职 SQL 不超过 D1 的 100 参数限制。前端续页去重、取消旧请求并忽略过期响应。

`GET /api/permissions` 返回权限目录及 `conditionProviders`（code、version、说明、parameterSchema）。保存和使用角色均验证条件版本与参数，未知配置不授予权限。当日岗位精确匹配校区、业务日、岗位和工作类型，任职及工作资格采用左闭右开有效区间。

## 账号与业务范围

`accounts.manage` 及校区范围决定账号管理和激活审批；基础类型为 technician 的成员也可执行明确授予的管理操作。基础类型保留系统安全等级，普通业务能力统一由角色授权决定。维修负责人可分配授权校区内的普通业务角色及工作资格，禁止修改本人或受保护系统身份；共享角色涉及本人或范围外成员时只可查看。授权与角色变更同时校验范围、有效期和并发版本。管理员邀请见 [业务规则](../requirements.md#成员账号与激活) 和 [身份映射](identity-mapping.md)。

预约列表将完整授权投影为 D1 条件，包括校区、归属成员、对象 ID 和当日岗位日期。姓名／学号搜索仅匹配具有 `customer.identity.read` 的记录，联系方式授权后才解密。列表、状态分面与总计使用相同可见范围，分面忽略当前状态选择，总计独立于当前页。

`GET /api/appointments` 默认及最多每页 200 条，React 每页 100 条；`nextCursor` 为不透明续页标记，排序追加稳定键，后续请求保持筛选与排序。新增条件须同步数据库投影及授权引擎对照测试，未支持条件拒绝列表授权。

考勤列表和导出按事实中的校区、部门快照逐项验证当前完整授权；业务日期只筛选历史事实，不能复活过期管理授权。历史审计缺少可可靠过滤的统一范围，受限审计授权拒绝全局读取。
